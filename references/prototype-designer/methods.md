# Prototype Designer · 方法库

> 原型是仪器，不是展品。
> 目标不是「把 IA 翻译成页面」，是用最便宜的方式让一个假设第一次可以被看见、被点击、被否定。

---

## 0. 工作顺序

```
选检验问题 → 写支持/反驳标准 → 选模式与保真度 → 做原型 → 自检 → 写学习日志 → 回灌
```

**铁律**：做之前先写「观察到什么算支持 / 什么算反驳」。事后补标准 = 事后解释。

---

## 1. 选检验问题

从赌注、需求、IA 中选**最不确定、且原型能回答**的一个问题。

### 1.1 什么问题适合原型

| 问题类型 | 适合原型？ | 例子 |
|---|---|---|
| 用户需要这个吗（Role） | ✅ 探索原型 | 「用户会不会用三级完成度？」 |
| 用户会用吗（Look & Feel） | ✅ 可点击原型 | 「用户能在 3 次点击内完成打卡吗？」 |
| 做得出来吗（Implementation） | ✅ WoZ / 技术原型 | 「没有后端能不能先模拟同步？」 |
| 长期动机/习惯维持 | ❌ 原型测不了 | 「三个月后还会用吗？」→ 纵向研究 |
| 真实社会情境/信任 | ❌ 原型测不了 | 「会不会推荐给朋友？」→ 真人访谈/行为研究 |

### 1.2 输出问题卡

```
检验的赌注/假设：B1 / A2 / IA-节点
最不确定的点：
原型能回答什么：
原型不能回答什么：
```

**一个问题不够具体，就不是问题。** 「看看用户喜不喜欢这个设计」不是检验问题。

## 2. 写支持/反驳标准（做之前）

| 观察到什么 | 判定 |
|---|---|
| [具体行为/原话/完成率] | 支持 |
| [具体行为/原话/完成率] | 反驳 |
| [需要真人/更高保真/更长周期] | 测不了 |

### 2.1 标准必须可观察

- ✅「5 人里有 4 人在 30 秒内找到微型版」
- ✅「3 人中有 2 人说『这让我觉得做少了也没关系』」
- ❌「用户觉得好用」
- ❌「界面看起来清楚」

### 2.2 判定线先于数据

先写死支持/反驳线，再看结果。否则会出现「其实用户只是没理解」这类事后解释。

### 2.3 顺序与措辞也要先控制

- **顺序平衡**：A/B 或多方向呈现时，顺序本身就是层级线索。至少做两组顺序（如 3/5 大→小、2/5 小→大），顺序进编码表；如果结果随顺序翻转，判「未定」。不能所有人先看同一个顺序，再把另一顺序排除在主判定外。
- **追问不提供词**：不要主动问「有没有觉得这不算/偷懒」。这会制造反驳词。用中性追问（「你会怎么向朋友描述？」），并区分「被试自发说出」与「追问带出」——只有自发语言计入主判定。
- **复合对照臂不归因单一变量**：如果对照版同时改了视觉权重、文案、圆环深度，就不能说「视觉平等有效/无效」；只能说「这个复合呈现有影响」。要归因，下一轮做单变量拆分。

## 3. Houde & Hill 原型三角

| 维度 | 回答 | 原型形态 |
|---|---|---|
| **Role** | 用户需要这个吗？ | 纸面/灰框/故事板；不做视觉 |
| **Look & Feel** | 用户会用吗？ | 可点击；真实内容；核心流 |
| **Implementation** | 做得出来吗？ | WoZ / 技术原型；不追求完整 |

**一个原型只回答一个维度。** 同时回答三个维度 = 过度设计。

---

## 4. 保真度阶梯

```
纸面/故事板 → 灰框 → 可点击 → 高保真 → WoZ/技术原型
```

| 保真度 | 适合回答 | 成本 | 风险 |
|---|---|---|---|
| 纸面/故事板 | Role、结构方向 | 最低 | 用户难以想象交互 |
| 灰框 | 结构、层级、信息密度 | 低 | 缺少真实内容时判断失真 |
| 可点击 | 核心流、状态、点击次数 | 中 | 容易过早抛光 |
| 高保真 | 视觉/品牌/情绪 | 高 | 用户被视觉吸引，不敢批评结构 |
| WoZ | 系统行为、人工替代 | 中 | 脚本不真实会污染结果 |

### 4.1 选择规则

**用能回答问题的最低保真。超过需要的保真度是负担。**

- 探索模式：纸面/灰框；**禁止颜色和品牌**。
- 验证模式：可点击；真实内容；覆盖空/错/加载。
- 模拟模式：WoZ 界面 + 人工脚本；明确哪些是演的。

### 4.2 过度抛光的代价

好看的 prototype 会让用户说「挺好的」，而不是说「我卡在这里」。视觉越完整，越难得到结构反馈。

## 5. 三种模式

### 5.1 探索模式（Role）

- ≥3 个**结构性不同**的方向，不是换色/换间距。
- 灰度；真实内容；每个方向写「它假设用户是谁、在什么时刻、怎么组织信息」。
- 产出：3 个方向 + 取舍表 + 哪个方向最值得进入验证。

### 5.2 验证模式（Look & Feel）

- 1 个聚焦原型；核心流可点击；无 dead end。
- 真实内容；覆盖空/错/加载/极端。
- 产出：可点击原型 + 任务脚本 + 成功线。

### 5.3 模拟模式（Implementation）

- WoZ 界面 + 人工脚本；明确「系统现在由人扮演」。
- 测真实行为，不写生产代码。
- 产出：界面 + 脚本 + 观察记录表。

## 6. 赌注检验矩阵

| 原型方向 | 检验的赌注 | 如果对，观察到什么 | 如果错，观察到什么 |
|---|---|---|---|
| A 三级等权 | A2 三级视觉平等不降低动机 | 多数人选简化/微型，且不报告「做少了也没关系所以不做完整」 | 用户只选完整，或认为微型是偷懒 |
| B 中性中断 | A5 中断不焦虑提高回归 | 中断后愿意回来，且不报告羞耻 | 用户觉得被放任，或根本不回来 |
| C 体感高光 | A3 体感记录有意义 | 用户愿意写，并能说出身体感受 | 用户跳过，或觉得是额外负担 |

**每个方向必须有「如果错」的观察。** 没有反驳条件的原型不是实验。

## 7. 制作纪律

### 7.1 真实内容

- 用用户原话、真实数据、真实任务；不用 Lorem Ipsum。
- 真实内容会暴露真实问题：长名字、空数据、错误输入、极端值。

### 7.2 可操作

- 核心流能点通；没有 dead end。
- 每个交互有反馈（哪怕是一个状态变化）。
- 明确标注「这是原型，不是产品」。
- **被试模式**：主试控制台、假设、A/B 差异、施测顺序不能与被试界面同屏。用 `?participant=1` 之类的开关隐藏主试材料；主试另开一份完整页面做控制。

### 7.3 状态覆盖

- 空 / 错 / 加载 / 极端数据至少各一个。
- 空状态是引导行动；错误是就地恢复。
- 不做的状态要写「这轮不测」。

### 7.4 版本与方向

- 每个方向独立文件/目录，不覆盖。
- 记录「这版改了什么、为什么改」。

---

## 8. 原型是毒药

每个原型必做三条自我审查：

1. **能 work ≠ 是最好的。** 这个方向能跑通，不代表它比别的方向好。
2. **如果这个方向全错了，可能是因为什么？** 写下来，别等用户说。
3. **用户是在评价原型，还是在评价我的设计？** demo 效应会污染反馈。

### 8.1 抛弃式 vs 生产代码

- 原型是抛弃式的：可以硬编码、可以假数据、可以人肉模拟。
- 不写生产代码、不做部署、不做完整架构。
- 明确写「这不是生产代码」。

## 9. 学习日志

做之前写，做之后补：

```
## 原型笔记
- 检验的赌注：
- 模式 / 保真度：
- 做之前以为：
- 做之后发现：
- 如果全错了可能是因为：
- 回灌信号：
```

### 9.1 做之后发现什么

- 结构问题：IA 节点放不下/找不到
- 状态缺失：状态矩阵漏了一个关键状态
- 交互卡住：用户必须完成 A 才能到核心价值
- 赌注问题：前提在原型里不成立

## 10. 回灌信号

| 信号 | 目标 | 何时发 |
|---|---|---|
| `IA_REVISIT` | Product Architect | 结构/导航/状态矩阵需要改 |
| `BET_ASSUMPTION_BROKEN` | Product Definer | 赌注前提在原型里不成立 |
| `MISSING_STATE` | Product Architect | 发现状态矩阵缺关键状态 |
| `REQUIREMENT_UNTESTABLE` | Requirements Analyst | 需求拆不出可测的原型 |

### 10.1 信号格式

```
🔄 信号：[类型]
目标：[岗位]
证据：[观察到什么]
建议：[需要重新审视什么]
```

**发现上游问题却沉默，是最严重的失职。**

## 11. 交接

### 给 UI Designer

- 哪些结构验证过了（可以做视觉）
- 哪些还是假设（要留退路）
- 哪些交互模式被证明有效/无效

### 给 Validation Researcher

- 这轮原型能测什么、不能测什么
- 测试脚本 + 成功线 + 已知偏差
- 样本要求（谁不能测）

### 给 Product Architect / Definer

- 回灌信号 + 证据 + 建议

## 12. 边界条件

| 情况 | 不要用原型 | 改用 |
|---|---|---|
| 长期习惯维持 | 单次原型测不了 | 纵向日记研究 |
| 真实社会情境/信任 | 实验室原型失真 | 现场研究/访谈 |
| 复杂动机 | 点击行为解释不了 | 深度访谈 |
| 技术可行性 | 原型能跑 ≠ 能生产 | 技术 spike + 工程评估 |
| 品牌/审美偏好 | 低保真测不了 | 高保真 + 人类评审 |

**诚实地写「这个原型测不了什么」，比假装能测更有价值。**

---

## 13. 输出原则

- 一个原型只回答一个问题。
- 用能回答问题的最低保真。
- 真实内容，不做 Lorem Ipsum。
- 支持/反驳标准先于数据。
- 每个方向都有「如果错」的观察。
- 发现上游问题就发信号，不默默绕过。
- 原型是仪器，不是展品；是抛弃式，不是生产代码。

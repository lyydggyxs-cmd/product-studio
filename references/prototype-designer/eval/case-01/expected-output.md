# Expected Output · Prototype Designer Eval Case 01（个人习惯工具）

> 一份合格产出必须包含以下内容。不要求选某个特定假设或模式；要求「一个问题、先写标准、低保真、可操作、有学习、有回灌」。
> 可接受的检验对象：A2（三级视觉平等）、A4（阶段标签可理解）、A5（中断不焦虑）；也可以选 IA 的结构假设，只要追到赌注且原型能回答。

## 1. 检验问题

- 明确选了一个最不确定、且原型能回答的假设
- 写清它追到 B1 / A1–A5 / 某个 IA 结构假设
- 写清「原型能回答什么 / 不能回答什么」
- 说明为什么先测这个假设（不确定性 × 决策影响）
- 不是「做一个完整 App 看看」

## 2. 支持 / 反驳标准（做之前写）

- 三类：支持 / 反驳 / 测不了
- 每条可观察（行为、原话、完成率、点击路径）
- 有阈值（例如 5 人里 ≥4 人）
- 标准先于数据；没有事后补写
- 有对应的观察方法（任务、访谈问题、行为记录）

## 3. 模式与保真度

- 明确模式：探索 / 验证 / 模拟
- 明确保真度：纸面 / 灰框 / 可点击 / WoZ
- 说明为什么这是「能回答问题的最低保真」
- 探索模式：灰度、禁止颜色/品牌
- 验证模式：核心流可点击、真实内容、状态覆盖
- 模拟模式：界面 + 人工脚本，明确哪些是演的

## 4. 原型

- 是可打开、可点、可读的东西（HTML / 纸面模板 / WoZ 界面）
- 不是 Markdown 描述
- 探索模式：≥3 个结构性不同方向；每个方向有假设、支持/反驳条件、取舍
- 验证模式：1 个聚焦原型；核心流无 dead end；每个交互有反馈
- 真实内容（用户原话、真实习惯名、真实错误）
- 标注「这是原型，不是产品」

## 5. 状态覆盖

- 空 / 错 / 加载 / 极端至少各一个，或明确写「这轮不测哪些状态、为什么」
- 每个状态写「用户看到什么 + 用户能做什么」
- 非快乐路径是重点，不是附录

## 6. 学习日志

- 做之前以为
- 做之后发现（意外 / 结构问题 / 状态缺失 / 交互卡住）
- 如果这个方向全错了，可能是因为
- 「能 work ≠ 是最好的」的反思
- 用户是在评价原型还是评价设计（demo 效应）的说明

## 7. 回灌

- 至少一条回灌信号（IA_REVISIT / BET_ASSUMPTION_BROKEN / MISSING_STATE / REQUIREMENT_UNTESTABLE）
- 信号带：类型 / 目标岗位 / 证据 / 建议
- 没有发现上游问题时，明确说「这轮没有发现需要回灌的上游问题」，而不是沉默

## 8. 边界

- 明确写「这个原型测不了什么」
- 长期动机 / 真实社会情境 / 品牌审美等，交给纵向研究 / 现场研究 / 高保真评审
- 不把「会用」推断成「会坚持」
- 不写生产代码、不做部署

## 9. 如果证据不足

如果无法确定该测哪个假设，**写「先做一个 3 方向纸面探索，再决定验证哪个」也是合格输出**——只要给出方向假设、支持/反驳标准和选择规则。假装确定才是失败。

# Expected Output · Product Architect Eval Case 02

> 一份合格产出必须包含以下内容。不要求选某个特定组织方式；要求结构成立、证据用对。

## 1. 竞争性心智模型

至少 2–3 种真正不同的组织方式，例如：
- **Decision/action**：需要我决定 / 需要我知道 / 无需行动
- **Inbox**：本周新报告，像邮件一样按到达时间
- **Team/person**：按团队成员分组
- **Time**：本周 / 上周 / 历史

每种：
- 组织原则
- 用户行为依据
- 在什么场景最优
- 在什么场景失效

**必须**说明当前选择和最危险替代假说。

## 2. 骨架 IA

- 一级 ≤5 个
- 每个一级下二级 ≤5 个
- 每个节点标 ✅/⚠️/🔮
- 每个一级区域有明确用户任务（管理者侧 + 写作者侧）
- 标签来自用户语言，不是「仪表板/工作流/资产」

**必须**体现赌注：读者侧、固定阅读时刻、决策请求、行动捕获。IA 里不能只有「报告列表」，要有「需要我做什么 / 行动」。

## 3. 完整 IA + 内容模型 + 导航

- 展开到第 3 层
- 定义 ≥3 种内容类型（周报、决策请求、行动、团队/成员）
- 定义字段、关系、跨界面一致性约束
- 导航模式说明（为什么是侧边栏/顶部/底部）

## 4. 用户流

至少两条核心流：
- **管理者**：周一 9:30 收到摘要 → 10 分钟内看 2–3 条决策请求 → 行动（回复/决策/改期）
- **写作者**：周五写周报 → 编码决策请求 → 提交

每条流：
- 起点（时间/状态/触发）
- 决策点 ≤3 个选项
- 错误恢复（就地修复）
- 改主意路径
- 非快乐路径：空/错/离开-回来/放弃/成长/极端

## 5. 状态矩阵

每个一级界面 8 状态：
- 默认/悬停/聚焦/按压/禁用/加载/错误/空
- 每个状态写「用户看到什么 + 用户能做什么」
- 空状态是引导行动，错误是具体恢复

## 6. 验证工具

- Card Sorting：卡片、参与者（管理者 + 写作者）、任务、成功线、结果→行动
- Tree Testing：任务、正确路径、成功线、结果→行动
- 陌生人测试：标签列表、问题、通过线

**必须**精确到一个研究员明天能执行。

## 7. 信心地图 + 致命假设

- 每个节点标 ✅/⚠️/🔮，汇总占比
- 3–4 个致命假设，每个有验证方式、如果错了的后果、回退到哪一步
- 明确说：哪些节点可以大胆设计，哪些要留退路

## 8. 如果证据不足

如果 Architect 判断证据不足以确定骨架，**写「骨架待验证，先做 card sorting/tree testing」也是合格输出**——只要给出可执行的验证工具和回退规则。
假装确定才是失败。

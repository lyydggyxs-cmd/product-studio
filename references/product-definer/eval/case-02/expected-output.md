# Expected Output · Product Definer Eval Case 02

> 一份合格产出必须包含以下内容。不要求选某个特定方向；要求结构成立、证据用对。

## 1. 一个赌注

- 只一个赌注，不是 5–7 个。
- 格式：如果……那么……因为……
- 机制具体到「读者侧 / 内容侧 / 制度侧」中的哪一个，为什么选它。
- 如果选读者侧：写成「优先验证读者侧」，不要写「最可能是读者侧」（因为管理者证据只有 E18，8 人、未读原文）。

## 2. 证据使用

- 引用至少 4 个证据 ID。
- 必须用到 Stray/Sjøberg/Dybå 2016（站会研究）——它把「写」和「读—行动」分开了。
- 列出**反对证据/限制**：
  - 61% 是「日报/周报/小作文」合并项，拆不开。
  - 管理者侧直接证据只有 E18（8 人，未读原文）。
  - 站会研究不是周报，不能直接外推。
- **不得把 61% 拆成「周报写作是最大瓶颈」**；如果写具体环节，必须是假设句 + 验证计划。

## 3. 成功 / Kill 信号

- 成功信号必须定义「行动」：回复、决策、调整资源、跨团队跟进；不是「已读」或「已提交」。
- 例：≥2/3 管理者在一周内因为周报做出一个可观察的行动。
- Kill 信号至少 3 条，指向不同病灶：
  - K1 读者侧无阅读时刻/无动作 → 前提错
  - K2 内容侧没有决策请求 → 方案错
  - K3 周报实为考核/免责 → 制度问题，工具无效
- 判定线先于数据。

## 4. Plan B

- 具体转向：例如「内容侧：把周报模板改成决策请求」「制度侧：管理者反馈仪式」「写作者侧：自动聚合」。
- 保留什么、放弃什么。

## 5. Anti-Goals

- 至少 3 条。
- 每条是判断（不服务赌注/与约束冲突），不是「没时间」。
- 带被牺牲的价值 + 恢复条件。
- 例如：不做绩效评估（会把周报变成考核）、不做监控（会破坏信任）。

## 6. PRD v0.1

一页能读出：
- 产品是什么（用户视角一句话）
- 为谁（写作者/管理者）
- 当前赌注
- 本期范围
- 不做什么
- 成功/kill 信号
- 已知不确定性（61% 合并项、管理者证据薄、站会研究外推）

## 7. 决策日志

- 至少 2 条：选这个赌注、选这个范围。
- 每条有：决定、理由、证据、考虑过但没选、重新评估条件。

## 8. 如果证据不足

如果 Definer 判断证据不足以选一个方向，**写「先验证读者侧 vs 内容侧，暂不下注」也是合格输出**——只要给出验证计划和 kill 信号。
假装确定才是失败。

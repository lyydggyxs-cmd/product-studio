# Brief · Design Critic Eval Case 01（个人习惯工具 UI）

## 评审对象

UI Designer 为「个人习惯工具」产出的高保真设计：

- `design-system.md`（设计意图 + 令牌 + 组件 + 视觉资产 + 页面清单）
- `ui-spec.md`（每页结构 / 状态 / 交互 / 文案 / 响应式）
- `design-rationale.md`（关键决策 + 大胆/退路/等验证 + 需人眼）
- `screens/`（6 屏 + 状态页：今天 / 完成 / 回顾 / 详情 / 空 / 中断回归 / 加载-错误-离线）
- `screens/_shots/`（真实截图，必须逐张看）

## 上游（对照用）

- `bet-book.md`：B1 赌注、成功/kill 信号、A1–A5
- `prd.md`：范围、Anti-goal、核心 Job
- `ia-flows.md`：4 个一级区域、用户流、状态矩阵、信心地图
- `requirements.md`：P0 ≤5、15 条 AC、边界、不做清单、冲突

## 任务

写一份 `critique.md`，回答：**这份设计是否忠实、完整、可使用？**

必须包含：

1. **评审范围**：对象 / 保真度 / 评什么 / 不评什么 / 输入
2. **意图对齐**：赌注 B1 / 核心 Job / 关键 AC / 品牌温度 / 信息密度，逐条 ✅/❌ + 证据
3. **问题清单**：
   - 🔴 阻断 / 🟡 重要 / 🟢 建议 / ⚪ 无法判断
   - 每个问题：位置 + 观察到什么 + 原则/场景 + 影响 + 路由
4. **覆盖检查**：空/错/加载/中断/极端/响应式/可访问性，逐项 ✅/❌
5. **路由建议**：Definer / Architect / UI / Validation / Requirements
6. **无法判断**：需人眼/真机/真人的项，诚实列出
7. **总判断**：✅ 可进入下一阶段 / ⚠️ 有保留 / ❌ 退回修改

## 硬规则

- 每个发现必须有证据（页面/组件/状态/截图/源码位置）。
- 每个发现必须标严重度；🔴 必须能回答「不改会怎样」。
- **不给方案**：不写「改成 X」「加一个 Y」；只描述问题与影响。
- **不做审美裁判**：不说「好看/不好看」；可验证的品质（对比度/层级/一致性）可以评，审美判断标 ⚪。
- **不越界评上游**：赌注/IA 问题标「需验证」+ 路由，不替 Definer/Architect 决策。
- 尊重 UI Designer 的声明：它说「这轮不测什么」，就不报那个维度；但可以质疑「你说在测 X，但 X 走不通」。

## 什么算成功

- 至少发现 2 个有证据的真问题（🟡 或 🔴），不是「整体不错」
- 严重度分级校准：不是全红/全绿；有 🟢/⚪
- 覆盖检查不是打勾，而是逐项给证据
- 问题路由正确：UI 能修的 vs 上游问题分开
- 「无法判断」诚实列出（审美、动效、字体回退、真人行为）
- 总判断明确，且被问题清单支撑

## 明确不做

- 不改设计文件、不重画、不写方案
- 不评生产代码质量
- 不评品牌识别/营销页
- 不替代真人测试

## 时间盒

40–50 分钟。优先保证「范围 → 意图对齐 → 3–5 个分级发现 → 覆盖 → 总判断」完整。

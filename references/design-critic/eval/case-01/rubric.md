## Case-specific 检查

| # | 检查项 | 通过标准 | 证据位置 |
|---|---|---|---|
| 1 | **范围锁定** | 对象/保真度/评什么/不评什么/输入写清 | |
| 2 | **意图对齐** | 对照 B1/Job/AC/温度/密度，逐条 ✅/❌ + 证据 | |
| 3 | **证据可定位** | 每个发现有页面/组件/状态/截图/源码位置 | |
| 4 | **严重度校准** | 🔴/🟡/🟢/⚪ 都有；不是全红/全绿；阻断能回答「不改会怎样」 | |
| 5 | **覆盖检查** | 空/错/加载/中断/极端/响应式/可访问性逐项 ✅/❌ | |
| 6 | **不给方案** | 不写「改成 X/加 Y」；只描述问题与影响 | |
| 7 | **路由正确** | 每个发现标归属；上游问题不越界 | |
| 8 | **总判断明确** | ✅/⚠️/❌ + 必须修/记录/不评三类；被问题清单支撑 | |

## 常见失败

- 「整体不错，建议继续优化」——没有 go/hold/no-go。
- 只评快乐路径，不看空/错/加载/中断/极端。
- 所有问题都是 🟢，或所有问题都是 🔴。
- 没有位置/证据，只有「层级不清」「不够醒目」。
- 给方案：改成 X、加 Y、用 Z。
- 越界评赌注/IA，没有用户证据。
- 把「无法判断」写成「没问题」。
- 不读 bet/IA/requirements，只看截图。
- 不路由，问题全部丢给 UI。

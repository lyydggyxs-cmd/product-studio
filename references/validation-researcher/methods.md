# Validation Researcher · 方法库

> 信条不是「验证我们做对了」，是**「找出产品哪里做错了」**。
> 你的结论决定团队继续、修正还是停；所以判定线必须先于数据，行为优先于言语，小样本必须诚实。

---

## 0. 工作顺序

```
定验证问题 → 选方法 → 写预注册计划 → 设计任务脚本 → 执行/模拟 → 合成 → 分流 → 报告 → 路由
```

**铁律**：判定线先于数据。结果出来后改线 = 事后解释。

---

## 1. 定验证问题

### 1.1 选 1–3 个问题

从赌注的成功/kill 信号出发，选**最不确定、最影响决策**的 1–3 个问题。

```
Q1：要回答什么？
- 支持证据：
- 反驳证据：
- 需要更多数据：
```

**不要**一次验证 10 个问题。问题太多 = 没有重点 = 什么都测不出来。

### 1.2 问题类型

| 问题 | 类型 | 方法 |
|---|---|---|
| 用户能不能完成核心 Job | 可用性 | 任务测试（moderated） |
| 用户想不想要 | 价值 | 价值访谈 + 行为观察 / 假门测试 |
| 结构对不对 | 结构 | Tree testing / 首 click 测试 |
| 视觉/交互是否困惑 | 交互视觉 | 任务测试 + 回放 |
| 是否会持续用 | 纵向 | 日记研究 / 纵向跟踪（本期可只设计，不执行） |

---

## 2. 写预注册计划

在收数据前写死：

```
样本：谁、多少、怎么招
条件：对照/实验、顺序、间隔
任务：场景包装、观察点、追问方向
判定线：支持 / 挑战 / 停止 / 需要更多数据
执行者：谁做、什么时候
偏差控制：主持人不引导、顺序平衡、盲法（如可行）
```

### 2.1 判定线

每条问题都必须有：

- **支持线**：观察到什么算支持
- **挑战线**：观察到什么算挑战
- **停止线**：观察到什么算 kill/pivot
- **需要更多数据**：什么情况无法判定

**判定线要可观察、有阈值、有分母。** 「用户喜欢」不是判定线。

---

## 3. 任务脚本

### 3.1 场景化，不是操作指令

| ❌ 操作指令 | ✅ 场景包装 |
|---|---|
| 「点击打卡按钮，看看结果」 | 「想象你今天早上完成了冥想，想记录下来。你会怎么做？」 |
| 「打开回顾页」 | 「一周过去了，你想看看这周过得怎么样。你会去哪里看？」 |
| 「测试空状态」 | 「你是第一次用这个产品，还没有任何记录。你会怎么开始？」 |

### 3.2 脚本结构

1. **热身**：建立信任，问最近一次相关行为（不是「你喜欢什么」）
2. **任务**：场景包装 + 观察点 + 不提示
3. **任务后追问**：中性、开放、问具体行为/原话
4. **汇总**：「如果只能用一句话描述这个产品……」
5. **收尾**：感谢、说明用途、允许撤回

### 3.3 观察点

每个任务写：
- 用户先看哪里？
- 在哪里停住/犹豫？
- 有没有出错？怎么恢复？
- 有没有求助？问什么？
- 完成/放弃的瞬间说了什么？

---

## 4. 主持人纪律

- **不引导**：不问「你觉得这个功能好用吗？」「你是不是觉得……」
- **不解释**：用户问「这是什么」，反问「你希望它是什么？」
- **等待**：用户卡住时等 ≥5 秒再给提示
- **回放**：用用户的原话复述，不替 TA 总结
- **不辩护**：用户批评设计时，不说「其实我们是这样想的」
- **记录原话**：不要只记「用户很满意」；记「用户说：『这个我今天就能用』」

---

## 5. 行为 vs 言语

### 5.1 行为优先

≥70% 的发现应基于用户**做了什么**，不是**说了什么**。

| 行为证据 | 言语证据 |
|---|---|
| 点击路径、完成时间、错误次数 | 「我觉得挺好」 |
| 在哪里停住、求助几次 | 「这个功能很有用」 |
| 放弃/返回/重复提交 | 「我会用」 |
| 选了哪一档、改了几次 | 「三档都差不多」 |

**「用户说喜欢」不能代替「用户能用/会用/会回来」。**

### 5.2 言语也要记

言语不是没用；它解释行为。但要区分：
- **自发原话**（不是追问带出）权重更高
- **追问带出**只作参考
- **社会赞许**（「挺好的」）权重最低

---

## 6. 模式 vs 个案

### 6.1 频率规则

- **≥3/5** 才能叫「模式」。
- 1–2 人的反应是**个案**，可以报，但不能写成「用户都」。
- 负向个案也要报，不能只报支持假设的。

### 6.2 严重度 × 频率

| | 高频（≥3/5） | 低频（1–2/5） |
|---|---|---|
| **阻塞** | 🔴 必须修 | 🟡 记录，可能是个案 |
| **重要** | 🟡 应修 | 🟢 观察 |
| **建议** | 🟢 可选 | ⚪ 记录 |

---

## 7. 价值 / 可用性 / 结构分流

| 类型 | 表现 | 路由 |
|---|---|---|
| **价值** | 用户不想要 / 不需要 / 不觉得值得 | Product Definer |
| **可用性** | 用户想要但不会用 / 找不到 / 操作失败 | UI Designer / Prototype Designer |
| **结构** | 用户找不到入口 / 标签不理解 / IA 不对 | Product Architect |
| **需求不可测** | AC 本身无法判断 | Requirements Analyst |
| **需更多证据** | 样本不足 / 结果混合 | 下一轮验证 |

**把可用性问题当价值问题，会导致错误地砍功能；反过来会错误地改界面。**

---

## 8. 小样本诚实

- n=3–5 只能发现**方向**，不能证明效应量、不能外推。
- 不要说「所有用户都……」；说「5 人里 4 人……」。
- 不要用百分比制造精确感（「80% 用户」= 4/5，样本太小）。
- 区分**探索性**（发现方向）与**确证性**（检验假设）；n=5 是探索性。
- 报告「如果前提错了，结论会怎样翻转」。

---

## 9. 偏差

| 偏差 | 表现 | 控制 |
|---|---|---|
| 样本偏差 | 只招到熟悉产品的人 | 明确画像；招极端/边缘用户 |
| 主持偏差 | 引导性提问、替用户总结 | 脚本预写；中立追问；回放原话 |
| 代理指标偏差 | 用「说喜欢」代替行为 | 行为优先；区分言语/行为 |
| Demo 效应 | 用户评价原型像不像产品 | 明确「这是原型」；任务优先 |
| 顺序效应 | A/B 顺序影响结果 | 顺序平衡；记录顺序 |
| 社会赞许 | 用户说「挺好的」 | 问具体行为/过去事件；不问未来意愿 |

**报告必须写：样本偏差、主持偏差、代理指标、无法判断的部分。**

---

## 10. 合成与报告

### 10.1 每条发现

```
现象：具体发生了什么
证据：原话/行为/时间戳/截图
频率：≥3/5 模式 / 1–2/5 个案
严重度：🔴/🟡/🟢/⚪
类型：价值 / 可用性 / 结构 / 交互视觉 / 需求不可测
路由：Definer / Architect / UI / Requirements / 下一轮
```

### 10.2 报告结构

1. **信号卡**：结论方向、置信度、翻转前提、与预注册的关系
2. **验证问题 → 结果 → 证据**
3. **模式 vs 个案**
4. **价值 vs 可用性 vs 结构**
5. **无法判断 / 偏差声明**
6. **迭代建议**：紧急 / 下版 / 探索
7. **路由与 kill/pivot 信号**

### 10.3 总判断

- **支持**：判定线满足，可以继续
- **挑战**：判定线被触发，需要修正
- **停止**：kill 信号触发，需要重想
- **需要更多数据**：样本/效度不足，不能判

**总判断必须被证据支撑，不能「整体不错」。**

---

## 11. 模拟数据声明

如果数据是模拟的（eval、dry-run、教学）：

- 在报告开头明确写「这是模拟数据，不是真人访谈」。
- 不得声称「用户说/用户做」；写「模拟会话 S1 显示……」。
- 结论只用于方法/流程验证，不能当产品证据。
- **假装做过访谈是最严重的失职。**

---

## 12. 输出原则

- 1–3 个问题；不要一次验证 10 个。
- 判定线先于数据；不事后改线。
- 任务场景化；主持人不引导。
- 行为优先；言语解释行为。
- ≥3/5 才是模式；1–2 人是个案。
- 区分价值/可用性/结构；路由到正确岗位。
- 小样本诚实；不夸大、不外推。
- 偏差和无法判断必须写。
- 模拟数据必须声明。

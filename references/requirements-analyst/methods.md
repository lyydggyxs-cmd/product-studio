# Requirements Analyst · 方法库

> 目标不是写更多需求，是把一个赌注拆成**可执行、可验证、可追溯**的最小闭环。
> 一条需求回答不了「服务哪个赌注、依据哪条证据、怎么算满足」，就不该存在。

---

## 0. 工作顺序

```
锁定赌注 → 写核心 Job Story → 拆最小闭环 → 写 AC → 补边界 → 写不做清单 → 追溯矩阵 → 冲突检测
```

**铁律**：P0 ≤ 5 条。超过 5 条，说明你在写 backlog，不是验证闭环。

---

## 1. 锁定赌注

开工前用一句话复述：

```
当前赌注：B1
如果 ______，那么 ______，因为 ______。
成功信号：______
Kill 信号：______
```

### 1.1 追溯检查

每条需求必须能回答：

| 问题 | 答不上来就 |
|---|---|
| 服务哪个赌注？ | 删掉 |
| 依据哪条证据（或标 🔮）？ | 补来源或降置信度 |
| 如果不做，赌注会怎样？ | 降优先级或删掉 |
| 怎么算满足？ | 写不出 AC 就不是需求 |

**需求不能追溯到赌注，就不是需求，是愿望。**

---

## 2. 核心 Job Story

### 2.1 格式

```
When [具体情境：时间/地点/情绪/设备/认知负荷/社会情境]，
I want to [动机，不是功能]，
so I can [可感知的结果]。
```

### 2.2 情境六要素

| 要素 | 问题 | 例子 |
|---|---|---|
| 时间 | 什么时候？ | 周三 21:40，洗完碗 |
| 地点 | 在哪？ | 厨房/地铁/床上 |
| 情绪 | 什么状态？ | 累、烦、想被照顾 |
| 设备 | 用什么？ | 手机、单手、2 分钟 |
| 认知负荷 | 能想多少？ | 不想做选择 |
| 社会情境 | 有谁在？ | 一个人/孩子在旁边 |

### 2.3 User Story vs Job Story

| ❌ User Story | ✅ Job Story |
|---|---|
| As a user, I want a habit tracker, so I can track habits. | When 周三晚上 9:40 洗完碗、只有 2 分钟、不想做选择，I want to 用最小动作完成今天的记录，so I can 不让这一天断掉。 |

**User Story 丢掉了情境；情境才是需求的锚点。**

---

## 3. 最小闭环需求

只写验证赌注所需的最小需求。每条：

```
ID：R01
Job Story：
服务赌注：B1
证据：E01 / E03（或 🔮）
如果不做会怎样：
优先级：P0 / P1 / P2
```

### 3.1 优先级判定

| 优先级 | 判定 |
|---|---|
| **P0** | 不做，赌注就无法验证 |
| **P1** | 影响体验，但不影响赌注验证 |
| **P2** | 优化项，可以延后 |

### 3.2 数量约束

- P0 ≤ 5 条。
- 每条 P0 必须是「验证赌注的最小闭环」的一环。
- 如果一条需求删掉后赌注仍可验证，它就不是 P0。

---

## 4. 验收标准（AC）

每条 P0 用 Given-When-Then：

```
Given [状态/情境]
When [操作]
Then [用户感知的结果]
```

### 4.1 AC 的四条硬规则

1. **一条只测一个假设**。一条 AC 里塞两个「Then」，就无法判断通过/不通过。
2. **从用户视角写**，不写技术实现。
3. **含时间/频率约束**（如「30 秒内」「连续 3 天」）。
4. **三条线**：通过线 / 证伪线 / 需要更多数据的线。

### 4.2 例子

| ❌ 不可测 | ✅ 可测 |
|---|---|
| 用户觉得打卡很顺畅 | Given 用户第一次打开，When 选择一档并点完成，Then 3 次点击内看到完成态，且不需要阅读说明 |
| 体验友好 | Given 昨天没有记录，When 今天打开，Then 用户看到中性提示 + 三个可选档位，不出现红色/「失败」字样 |
| 统计功能完整 | Given 用户有 7 天记录，When 打开回顾，Then 首屏显示本周完成率（数字 ≥ 正文 3 倍），且能说出这个数字的含义 |

### 4.3 证伪线

每条 AC 必须写：

- **通过线**：什么算满足
- **证伪线**：什么算不满足
- **需要更多数据**：什么情况无法判定（样本不足、理解失败、demo 效应）

---

## 5. 边界条件

| 状态 | 需求应该做什么 |
|---|---|
| **空** | 第一次使用、无数据：引导行动，不是「暂无数据」 |
| **错误** | 网络断、保存失败、数据异常：就地恢复 + 数据不丢 |
| **离开-回来** | 中断后重新开始：不羞辱、允许回归 |
| **放弃** | 用户想停：允许暂停/归档，不制造负罪感 |
| **成长** | 从新手到熟练：入口/默认值/文案随阶段变化 |
| **极端** | 超长文本、超多数据、极端高频、部分失败 |

**每条 P0 至少覆盖空 / 错 / 离开-回来中的两个；不覆盖的要写「为什么这轮不测」。**

---

## 6. 歧义检测

看到这些词，必须翻译成可观察条件：

| ❌ 歧义词 | ✅ 可观察条件 |
|---|---|
| 流畅 | 3 次点击内完成；无 loading 超过 1.5s |
| 友好 | 不出现红色/失败语言；空状态有下一步 |
| 专业 | 文案不用内部术语；标签能被陌生人猜中 |
| 有温度 | 具体场景文案，不是通用鼓励语 |
| 简单 | 首次使用不需要说明；选项 ≤3 |
| 及时 | 在 [具体时刻] 前出现；延迟 ≤ [具体秒数] |

**写不出可观察条件，说明你还没想清楚。**

---

## 7. 不做清单

每条不做的需求，写三件事：

| 项 | 要求 |
|---|---|
| **为什么不做** | 是判断（「不服务核心赌注」），不是资源（「没时间」） |
| **被牺牲的价值** | 承认它本来能带来什么 |
| **恢复条件** | 什么情况下重新考虑 |

### 7.1 判断 vs 资源

| ❌ 资源伪装 | ✅ 判断 |
|---|---|
| 这个需求很好，但 V1 没时间 | 这个需求服务次要赌注，核心赌注还没验证，先不做 |
| 做不了 | 判断后不应该做；如果核心赌注变了，恢复条件见下 |

---

## 8. 追溯矩阵

| 需求 | 赌注 | 证据 | AC | 优先级 |
|---|---|---|---|---|
| R01 | B1 | E01 / E03 | AC1 | P0 |
| R02 | B1 | E07 | AC2 | P0 |

### 8.1 检查

- 每条 P0 都能追到赌注和证据。
- 没有孤立需求（不能和任何其他需求形成强化关系）。
- 没有两条需求基于相反假设。

---

## 9. 需求 vs 方案

| ❌ 需求里写方案 | ✅ 写结果 |
|---|---|
| 用弹窗提醒用户 | 用户需要在合适时刻被告知可以开始 |
| 首页放一个圆环 | 用户需要一眼看到今天完成了多少 |
| 加一个「跳过」按钮 | 用户需要在不做的时候不被惩罚 |

**方案留给 Architect / UI；需求只写「用户需要什么结果」。**

---

## 10. 需求冲突检测

两条需求如果基于相反假设，不能同时进 MVP：

| 冲突类型 | 例子 | 处理 |
|---|---|---|
| 默认值冲突 | 「默认推完整档」vs「三档平等」 | 明确默认值是否算推荐；改需求或改假设 |
| 提醒频率冲突 | 「每天提醒」vs「不制造压力」 | 定义提醒的触发条件与语气 |
| 数据语义冲突 | 「完成次数」vs「完整次数」 | 先定义计数语义，再写统计需求 |
| 社交冲突 | 「排行榜激励」vs「不做比较」 | 删除一个，或明确隔离 |

**发现冲突，写成「需要 Definer 决策」的反哺，不要自己默默选一个。**

---

## 11. 交接

### 给 Product Architect

- 核心 Job + 需求 + AC + 边界条件
- 明确说：哪些是硬约束，哪些可以调整

### 给 Prototype Designer / UI Designer

- 每条需求的 AC 和情境
- 哪些状态必须覆盖

### 给 Validation Researcher

- 可测的 AC 和通过/证伪线
- 哪些需求不可测、需要换成什么方法

### 向 Product Definer 反哺

- 「这个赌注拆不出可验证的需求」
- 「两条需求基于相反假设，不能同时进 MVP」

---

## 12. 输出原则

- 每条需求服务一个赌注；说不出来就删掉。
- Job Story 有情境；不是 User Story。
- P0 ≤ 5 条；只为验证赌注的最小闭环写需求。
- AC 可测；一条只测一个假设；有通过/证伪/需更多数据三条线。
- 边界条件覆盖空/错/离开-回来/放弃/成长/极端。
- 不做清单是判断，不是资源。
- 不把方案写进需求。
- 发现需求冲突，交给 Definer 决策，不默默选一个。

# Brief · Requirements Analyst Eval Case 01（个人习惯工具）

## 产品

一个给个人用的习惯养成工具：1–3 个习惯，每天一次轻量记录，按「触发 → 微小行动 → 意义 → 体感 → 身份」的四维模型设计。
移动端优先，个人使用，不做社交、排行榜、企业后台。

## 本次任务

把 Product Definer 的赌注 B1 拆成**可执行、可验证、可追溯**的需求包。

产出 `requirements.md`，包含：

1. **核心 Job Story**（至少 2 条：一条日常完成，一条中断后回归）
2. **需求清单**：P0 ≤ 5 条；每条有 ID、Job Story、服务赌注、证据、如果不做会怎样、优先级
3. **验收标准**：每条 P0 的 Given-When-Then，含通过线 / 证伪线 / 需要更多数据的线
4. **边界条件**：空 / 错 / 离开-回来 / 放弃 / 成长 / 极端
5. **不做清单**：判断 + 被牺牲价值 + 恢复条件
6. **追溯矩阵**：需求 → 赌注 → 证据 → AC → 优先级
7. **冲突标记**：发现需求之间基于相反假设时，给选项 + 需要谁决策

## 输入

| 输入 | 来自 | 读什么 |
|---|---|---|
| `evidence-base.md` | Research Analyst | 四维模型、三个真实案例、已知的未知 |
| `bet-book.md` | Product Definer | B1、成功/kill 信号、致命假设 A1–A5 |
| `prd.md` | Product Definer | 范围、Anti-goal、核心 Job |
| `open-questions.md` | Studio Lead | 与需求相关的未决问题 |

## 硬规则

- 每条需求必须追溯到 B1 / A1–A5 / 明确证据；无来源的标 🔮。
- 用 Job Story（When / I want to / so I can），不用 User Story。
- P0 ≤ 5 条；只为验证 B1 的最小闭环写需求。
- 每条 P0 的 AC 必须可判断通过/不通过；一条只测一个假设。
- 边界条件覆盖空 / 错 / 离开-回来 / 放弃 / 成长 / 极端。
- 不做清单是判断，不是「没时间」。
- 需求里不写 UI 方案（不写「放一个圆环」「用苔绿色」）。
- 发现需求冲突，标出来交给 Definer 决策，不默默选一个。

## 什么算成功

- 5 条 P0 构成「打卡 → 中断回归 → 完成反馈 → 回顾 → 暂停」的最小闭环
- 每条 AC 能在 5 人原型测试或试点里判断通过/不通过
- 边界条件不是附录，是需求的一部分
- 不做清单有真正的取舍，不是资源借口
- 至少发现一个需求冲突，并给出决策选项
- 下游（Architect / Prototype / UI / Validation）能直接使用

## 明确不做

- IA / 用户流 / 状态矩阵（Architect 的职责）
- 视觉方案 / 组件 / 文案（UI 的职责）
- 排期 / 资源计划
- 功能 backlog：社交、排行榜、健康数据、订阅、多用户

## 时间盒

40–50 分钟。优先保证「5 条 P0 + 可测 AC + 边界 + 不做清单 + 冲突」完整。

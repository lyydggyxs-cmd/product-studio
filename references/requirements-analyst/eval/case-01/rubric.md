## Case-specific 检查

| # | 检查项 | 通过标准 | 证据位置 |
|---|---|---|---|
| 1 | **赌注锁定** | 一句话复述 B1；成功/kill 信号；需求只服务 B1 | |
| 2 | **Job Story 情境** | ≥2 条；含时间/地点/情绪/认知负荷；动机不是功能 | |
| 3 | **最小闭环** | P0 ≤5；构成「打卡 → 中断回归 → 完成反馈 → 回顾 → 暂停」闭环 | |
| 4 | **AC 可测** | 每条 P0 有 Given-When-Then；一条只测一个假设；有通过/证伪/需更多数据 | |
| 5 | **边界条件** | 覆盖空/错/离开-回来/放弃/成长/极端中的 ≥4 个 | |
| 6 | **歧义消除** | 关键形容词翻译成可观察条件 | |
| 7 | **不做清单** | 判断 + 被牺牲价值 + 恢复条件；至少一条「有资源也不做」 | |
| 8 | **冲突检测 + 交接** | 至少一个真实冲突 + A/B 选项 + 需要谁决策；下游知道硬约束/可调整 | |

## 常见失败

- 需求写成 10+ 条功能 backlog。
- 用 User Story 代替 Job Story。
- AC 不可测（「体验流畅」）。
- 只有快乐路径；空/错/中断/放弃/极端缺失。
- 不做清单是「V1 没时间」。
- 需求里写 UI 方案（圆环、颜色、组件）。
- 没有追溯矩阵。
- 没有发现「默认预选微型」vs「三档平等」的冲突。
- 把「做不了」写成「不做」。

# Expected Output · Requirements Analyst Eval Case 01（个人习惯工具）

> 一份合格产出必须包含以下内容。不要求需求条目完全一致；要求「可追溯、有情境、最小闭环、可测、有边界、有取舍、有冲突检测」。

## 1. 赌注锁定

- 一句话复述 B1：如果……那么……因为……
- 成功信号与 kill 信号
- 明确这轮需求只服务 B1，不服务其他方向

## 2. 核心 Job Story（≥2 条）

- 日常完成：When 具体情境（时间/地点/情绪/认知负荷），I want to 动机，so I can 可感知结果
- 中断后回归：When 昨天没有记录、今天再次打开，I want to 不被评判地继续，so I can 不让这一天断掉
- 每条标注服务赌注、证据、如果不做会怎样

## 3. 需求清单（P0 ≤5）

- 每条有 ID、Job Story、服务赌注、证据、如果不做会怎样、优先级
- 5 条 P0 构成最小闭环：打卡 → 中断回归 → 完成反馈 → 回顾 → 暂停
- 没有功能 backlog；P1/P2 不挤进 P0
- 需求写「用户需要什么结果」，不写 UI 方案

## 4. 验收标准

- 每条 P0 有 Given-When-Then
- 可判断通过/不通过；一条只测一个假设
- 含时间/频率约束
- 每条有三条线：通过线 / 证伪线 / 需要更多数据的线
- 从用户视角写，不写技术实现

## 5. 边界条件

覆盖空 / 错 / 离开-回来 / 放弃 / 成长 / 极端中的 ≥4 个：
- 空：第一次使用 / 无数据 → 引导行动
- 错：保存失败 / 离线 → 数据不丢 + 就地恢复
- 离开-回来：昨天没做 → 中性提示 + 三档
- 放弃：暂停习惯 → 不显示失败
- 成长：从启动期到形成期 → 文案/入口变化
- 极端：累计 30 次 / 超长文本 / 多习惯

不覆盖的写「为什么这轮不测」。

## 6. 不做清单

- 每条有判断（不是「没时间」）、被牺牲价值、恢复条件
- 至少有一条「有资源也不做」的判断（如社交/排行榜与 B1 冲突）
- 不把「做不了」写成「不做」

## 7. 追溯矩阵

| 需求 | 赌注 | 证据 | AC | 优先级 |
|---|---|---|---|---|

- 每条 P0 能追到赌注和证据
- 没有孤立需求
- 没有两条需求基于相反假设（或已标冲突）

## 8. 冲突检测

- 至少发现一个真实冲突（例如「中断态默认预选微型」vs「三档平等」；「计数语义：记录次数 vs 完整次数」）
- 给选项 A/B，说明各自代价
- 标「需要 Definer 决策」
- 决策前不把任何一版写成 P0 AC

## 9. 交接

- 给 Architect：核心 Job + 需求 + AC + 边界条件；哪些是硬约束、哪些可调整
- 给 Prototype / UI：必须覆盖的状态
- 给 Validation：可测的 AC 和通过/证伪线
- 给 Definer：至少一条反哺（冲突 / 不可测 / 赌注拆不出需求）

## 10. 如果证据不足

如果某条需求无法追溯到 B1，**写「这条需求暂不进入 P0，需要更多证据」也是合格输出**——只要说明缺什么证据、怎么补。把 🔮 写成 ✅ 才是失败。

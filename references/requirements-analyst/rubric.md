# Requirements Analyst · 评分标准

> 用于评审 Requirements Analyst 的产出，或用于 eval。
> 0–4 锚点；不是打分游戏，是诊断工具。

---

## 评分维度

| # | 维度 | 核心问题 |
|---|---|---|
| 1 | **赌注锁定与追溯** | 每条需求能追到赌注 / 证据 / 优先级吗？ |
| 2 | **Job Story 情境** | 有具体时间/地点/情绪/认知负荷吗？还是 User Story？ |
| 3 | **最小闭环纪律** | P0 ≤5 条吗？是验证赌注的最小闭环，还是功能 backlog？ |
| 4 | **AC 可测** | Given-When-Then 可判断通过/不通过吗？一条只测一个假设吗？ |
| 5 | **边界条件** | 空 / 错 / 离开-回来 / 放弃 / 成长 / 极端覆盖了吗？ |
| 6 | **歧义消除** | 「流畅/友好/专业」被翻译成可观察条件了吗？ |
| 7 | **不做清单与取舍** | 是判断还是资源？有被牺牲价值与恢复条件吗？ |
| 8 | **交接与冲突检测** | 下游知道硬约束/可调整吗？发现需求冲突并交给 Definer 吗？ |

---

## 0–4 锚点

| 分 | 含义 | 通用表现 |
|---|---|---|
| **0** | 缺失 | 完全没有这个维度 |
| **1** | 提名 | 提到概念，但没有执行 |
| **2** | 部分 | 有执行，但明显不足 / 不一致 |
| **3** | 合格 | 达到标准，可用于决策 |
| **4** | 示范 | 不仅达标，还能作为模板 |

### 1. 赌注锁定与追溯

| 分 | 表现 |
|---|---|
| 0 | 没有赌注，直接列需求 |
| 1 | 提到赌注，但需求是通用功能清单 |
| 2 | 部分需求能追溯，部分不能 |
| 3 | 每条需求有赌注/证据/优先级；有追溯矩阵 |
| 4 | 还给每条需求写了「如果不做，赌注会怎样」和置信度 |

### 2. Job Story 情境

| 分 | 表现 |
|---|---|
| 0 | 没有 Job Story |
| 1 | 用 User Story（As a...），情境丢失 |
| 2 | 有 When/ I want/ so I can，但情境泛化（「用户想记录」） |
| 3 | 情境含时间/地点/情绪/认知负荷至少 3 项；动机不是功能 |
| 4 | 情境能直接推导设计决策；不同 Job 的情境真正不同 |

### 3. 最小闭环纪律

| 分 | 表现 |
|---|---|
| 0 | 功能 backlog，没有优先级 |
| 1 | P0 > 8，或没有「最小闭环」概念 |
| 2 | P0 ≤8，但部分需求删掉后赌注仍可验证 |
| 3 | P0 ≤5；每条是验证赌注的最小闭环的一环 |
| 4 | 还说明了「为什么是这 5 条，而不是其他」和删除标准 |

### 4. AC 可测

| 分 | 表现 |
|---|---|
| 0 | 没有 AC |
| 1 | AC 不可测（「体验流畅」） |
| 2 | 有 Given-When-Then，但缺通过线/证伪线，或一条测多个假设 |
| 3 | 每条 P0 有 Given-When-Then；可判断通过/不通过；一条只测一个假设 |
| 4 | 还写了通过线/证伪线/需要更多数据三条线，以及观察方法 |

### 5. 边界条件

| 分 | 表现 |
|---|---|
| 0 | 没有边界条件 |
| 1 | 只有快乐路径 |
| 2 | 覆盖空/错中的 1–2 个 |
| 3 | 覆盖空 / 错 / 离开-回来 / 放弃 / 成长 / 极端中的 ≥4 个 |
| 4 | 每个边界都有对应需求/AC；不覆盖的写明「为什么这轮不测」 |

### 6. 歧义消除

| 分 | 表现 |
|---|---|
| 0 | 全是「流畅/友好/专业」 |
| 1 | 有歧义词，未翻译 |
| 2 | 部分翻译，但仍有关键词不可观察 |
| 3 | 所有关键形容词都翻译成可观察条件 |
| 4 | 还建立了「歧义词 → 观察条件」对照表，交给下游复用 |

### 7. 不做清单与取舍

| 分 | 表现 |
|---|---|
| 0 | 没有不做清单 |
| 1 | 只有「没时间/做不了」 |
| 2 | 有判断，但缺被牺牲价值或恢复条件 |
| 3 | 每条不做有判断 + 被牺牲价值 + 恢复条件 |
| 4 | 还区分了「有资源也不做」与「以后可能做」，并说明判断依据 |

### 8. 交接与冲突检测

| 分 | 表现 |
|---|---|
| 0 | 只交需求，没有交接 |
| 1 | 交接含糊，下游不知道硬约束/可调整 |
| 2 | 有交接，但没有冲突检测 |
| 3 | 明确硬约束/可调整/必须覆盖的状态；发现冲突并标出 |
| 4 | 冲突给选项 + 需要谁决策 + 决策前不写死 AC；还给 Definer/Architect 具体反哺 |

---

## 门控规则

以下任意一条触发，**退回重做**：

- **维度 1 = 0**：需求无法追溯到赌注 → 这是愿望清单，不是需求。
- **维度 3 = 0**：功能 backlog、没有最小闭环 → 无法验证赌注。
- **维度 4 = 0**：没有可测 AC → 做完不知道是否满足。
- **维度 6 ≤ 1**：关键需求全是不可观察的形容词 → 下游无法实现/验证。

## 总分参考

| 总分（8 维，满分 32） | 判断 |
|---|---|
| 28–32 | 可作为模板 |
| 22–27 | 可进入下游 |
| 16–21 | 需修正后重审 |
| < 16 | 退回 |

> 总分只作参考；门控优先。
